쿠버네티스(K8s) 실무 — 아키텍처, 설치, 운영 명령어, 네임스페이스

쿠버네티스(Kubernetes, K8s)는 여러 대의 서버(노드)를 하나의 클러스터로 묶어 컨테이너를 자동으로 배포·관리해 주는 오케스트레이션 도구입니다. 이 단원에서는 클러스터를 이루는 컴포넌트의 역할, Minikube와 kubeadm으로 클러스터를 직접 설치하는 과정, 실무에서 매일 쓰는 kubectl 명령어, 그리고 멀티 테넌시의 기본 단위인 네임스페이스까지 정리합니다.

1. K8s 개요

쿠버네티스 클러스터는 크게 클러스터를 제어하는 Master Node(컨트롤 플레인)와 실제로 컨테이너가 실행되는 Worker Node, 그리고 필요에 따라 추가로 설치하는 애드온 컴포넌트로 구성됩니다.

Master Node 컴포넌트

  • kubectl — K8s 클러스터를 조작하기 위한 가장 빈번하게 이용되는 커맨드 라인 인터페이스(CLI)입니다. 사용자가 클러스터에 명령을 전달하는 주요 도구입니다.
  • kube-apiserver — 클러스터의 중심 허브입니다. kubectl 등의 API 클라이언트로부터 오는 REST 요청을 검증하고, API 오브젝트를 구성하고 상태를 보고합니다. 모든 컴포넌트는 이 API Server를 통해서만 통신합니다.
  • kube-scheduler — 새로 생성된 모든 Pod에 대해 실행할 최적의 노드를 선택합니다. 각 노드의 리소스 상황, 제약 조건 등을 점수로 계산하여 가장 높은 점수를 받은 노드에 Pod를 배정합니다.
  • kube-controller-manager — 다양한 컨트롤러를 구동하는 마스터상의 컴포넌트입니다. 노드가 다운되었는지 감시하는 Node Controller, 복제본 수를 관리하는 Replication Controller 등이 포함됩니다.
  • etcd — 클러스터의 모든 관리 데이터가 저장되는 분산 키/값 저장소입니다. CoreOS가 개발했으며, 신뢰성이 요구되는 핵심 데이터의 저장 및 접근을 위해 설계되었습니다.
  • cloud-controller-manager — API를 통해서 클라우드 서비스와 연계하는 컨트롤러로, AWS, GCP 등 각 클라우드 업체에서 개발합니다.

Worker Node 컴포넌트

  • kubelet — 각 워커 노드에서 실행되며, 파드와 컨테이너의 실행을 담당합니다. 파드와 노드의 상태를 API 서버에 보고하고, 컨테이너 동작을 확인하는 프로브(Probe)를 실행합니다. 내장된 cAdvisor를 통해 메트릭을 수집합니다.
  • kube-proxy — 각 노드에서 동작하며 로드밸런싱 기능을 제공합니다. 서비스와 파드의 변경을 감지하여 iptables 규칙을 관리하고, 서비스명과 ClusterIP를 내부 DNS에 등록합니다.
  • CoreDNS — 파드가 서비스 이름으로부터 IP 주소를 얻기 위해 사용됩니다. 버전 1.11부터 kube-dns 대신 CoreDNS가 사용되었으며, 신뢰성과 보안성, 유연성이 개선되었습니다.

애드온 컴포넌트

  • kube-flannel — 모든 노드에서 실행되어 여러 노드 사이에서 IPv4 네트워크를 제공합니다. 이에 따라 컨테이너(파드)는 클러스터 내부의 IP 주소를 바탕으로 다른 노드의 파드와 통신할 수 있습니다. 네트워크 접근 제어가 필요한 경우에는 Calico를 사용합니다.
  • calico-kube-controllers — Calico를 위한 컨트롤러로, 데이터 스토어로서 etcd를 이용하기 위하여 사용됩니다.
  • calico-node — 모든 노드에서 실행되어 노드 간 파드의 통신, 라우팅, 네트워크 접근 관리 기능을 제공합니다.
  • kubernetes-dashboard — 클러스터를 시각적으로 관리할 수 있는 Web 대시보드입니다.
  • metrics-server — Heapster(v1.11에서 중단)를 대신하여 v1.8부터 도입되었습니다. API의 aggregation layer를 통해서 클러스터 전체로부터 메트릭을 수집합니다.

용도 설치 도구 설명
개발/학습 Minikube 로컬 환경에서 단일 노드 K8s 클러스터를 실행. 가장 쉬운 학습 방법

실습 환경 구축 — 공통 설정 (모든 노드)

실습은 Master(VM) / Node_1(VM) / Node_2(VM) 3대의 가상머신으로 kubeadm 기반 다중 노드 클러스터를 구성합니다.

# swap 비활성화 (K8s에서 필수)
sudo swapoff -a
sudo vi /etc/fstab   # swap 라인 주석 처리

# IP 포워딩 활성화(echo만 해도 됨)
sudo sh -c 'echo 1 > /proc/sys/net/ipv4/ip_forward'

# hosts 파일에 노드 등록
sudo vi /etc/hosts
# 아래와 같이 추가 (IP는 각자 환경에 맞게)
192.168.75.137 master
192.168.75.136 worker01
192.168.75.138 worker02

# 호스트명 변경 (변경하지 않으면 오류 발생!)
hostnamectl set-hostname master   # 또는 worker01, worker02
systemctl restart systemd-hostnamed

주의사항 — K8s에서는 swap이 켜져 있으면 문제가 발생할 수 있으므로 반드시 꺼야 합니다. 재부팅 후에도 유지되도록 /etc/fstab에서 swap 부분을 주석 처리해주세요.

실습 환경 구축 — 2단계: Docker 설치 (모든 노드)

# 필수 패키지 설치
sudo apt-get update
sudo apt-get install -y apt-transport-https ca-certificates curl gnupg lsb-release

# Docker 공식 GPG 키 추가
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | \
  sudo gpg --dearmor -o /usr/share/keyrings/docker-archive-keyring.gpg

# Docker 저장소 추가
echo "deb [arch=amd64 signed-by=/usr/share/keyrings/docker-archive-keyring.gpg] \
  https://download.docker.com/linux/ubuntu $(lsb_release -cs) stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

# Docker 설치
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io

# Docker 데몬 설정 (cgroup driver를 systemd로)
sudo mkdir /etc/docker
cat <<EOF | sudo tee /etc/docker/daemon.json
{
  "exec-opts": ["native.cgroupdriver=systemd"],
  "log-driver": "json-file",
  "log-opts": { "max-size": "100m" },
  "storage-driver": "overlay2"
}
EOF

# Docker 서비스 시작
sudo systemctl enable docker
sudo systemctl daemon-reload
sudo systemctl restart docker

실습 환경 구축 — 3단계: kubeadm, kubectl, kubelet 설치 (모든 노드)

cat <<EOF | sudo tee /etc/modules-load.d/k8s.conf

cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf

# K8s 저장소 추가 및 설치

echo 'deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.30/deb/ /' | sudo tee /etc/apt/sources.list.d/kubernetes.list

sudo apt-get update
sudo apt-get install -y kubelet kubeadm kubectl
sudo apt-mark hold kubelet kubeadm kubectl   # 자동 업데이트 방지

3. K8s 명령어 정리

Pod 조회 및 관리

장애 대응 시 가장 먼저 치는 명령어들입니다.

kubectl get pods -A                       # 전체 네임스페이스 Pod 목록
kubectl get pods -o wide                  # Pod가 뜬 노드, IP까지 확인
kubectl describe pod <pod명>               # Pod 상세 정보 (에러 원인 확인 시 핵심)
kubectl delete pod <pod명>                  # Pod 삭제 (재시작 유도)
kubectl exec -it <pod명> -- /bin/bash      # Pod 컨테이너 내부 접속

배포 관리 (Deployment)

배포, 롤백, 스케일링, NodePort 노출까지 실무에서 매일 쓰는 명령어입니다.

kubectl apply -f <파일명>.yaml                                  # YAML 적용 (배포 기본, 멱등성 보장)
kubectl set image deployment/<이름> <컨테이너명>=<이미지:태그>    # 이미지 버전 변경 (배포)
kubectl rollout undo deployment/<이름>                          # 직전 버전으로 롤백
kubectl scale deployment/<이름> --replicas=3                    # 파드 개수 조정
kubectl expose deployment <이름> --type=NodePort --port=80 --target-port=8080  # NodePort로 즉시 외부 노출

NodePort로 노출한 뒤에는 kubectl get svc <서비스명>으로 할당된 포트(30000~32767 범위)를 확인하고, curl <노드IP>:<NodePort>로 접속 테스트합니다.

클러스터 & 컨텍스트

kubectl config get-contexts              # 사용 가능한 컨텍스트 목록
kubectl config use-context <컨텍스트명>   # 컨텍스트(클러스터) 전환
kubectl config set-context --current --namespace=<네임스페이스>  # 기본 네임스페이스 변경
kubectl get nodes -o wide                # 노드 목록, IP, 상태 확인
kubectl cluster-info                     # 클러스터 기본 정보 확인

로그 확인

kubectl logs -f <pod명>                    # 실시간 로그 스트리밍
kubectl logs <pod명> --previous            # 재시작 전(크래시 이전) 로그 확인
kubectl logs <pod명> --since=1h            # 최근 1시간 로그만 확인
kubectl logs -l app=<라벨값>                # 라벨로 여러 Pod 로그 한 번에 확인
kubectl logs <pod명> -c <컨테이너명>        # 멀티 컨테이너 Pod에서 특정 컨테이너 로그

디버깅 & 트러블슈팅

kubectl get events --sort-by='.lastTimestamp'   # 클러스터 이벤트, 시간순 정렬
kubectl top pod                                 # Pod별 CPU/메모리 사용량
kubectl top node                                # 노드별 CPU/메모리 사용량
kubectl get pod <pod명> -o yaml                  # Pod 전체 스펙/상태 확인
kubectl debug <pod명> -it --image=busybox       # 디버깅용 임시 컨테이너 붙이기

Service & Ingress

kubectl get svc                             # Service 목록 (NodePort 등 포트 정보 포함)
kubectl describe svc <서비스명>               # Endpoints(연결된 실제 Pod) 확인
kubectl get endpoints                       # Service에 연결된 Pod IP 확인
kubectl port-forward svc/<서비스명> 8080:80   # 로컬에서 클러스터 내부 서비스 임시 접근
kubectl get ingress                         # Ingress 목록 확인

ConfigMap & Secret

kubectl get configmap                                          # ConfigMap 목록
kubectl describe configmap <이름>                                # ConfigMap 내용 확인
kubectl get secret                                              # Secret 목록
kubectl create configmap <이름> --from-file=<파일경로>            # 파일 기반 ConfigMap 생성
kubectl create secret generic <이름> --from-literal=key=value    # Secret 즉석 생성

권한 확인

kubectl auth can-i create pods                # 현재 계정 권한 확인
kubectl auth can-i create pods --as=<유저명>    # 특정 유저 권한 확인
kubectl get rolebinding,clusterrolebinding -A  # 전체 권한 바인딩 확인

참고: 자주 쓰는 옵션 조합

kubectl get pods --sort-by=.metadata.creationTimestamp   # 생성 시간순 정렬
kubectl get pods -o json | jq '.items[].metadata.name'    # jq와 조합해 원하는 필드만 추출
kubectl get pods -l app=<라벨값>,env=prod                  # 다중 라벨 필터링

4. minikube 실습

공식 문서: https://minikube.sigs.k8s.io/docs/

Minikube로 단일 노드 클러스터를 띄운 뒤, kubectl이 별도로 설치되어 있지 않아도 minikube kubectl -- 형태로 내장된 kubectl을 그대로 사용할 수 있습니다.

minikube start
minikube kubectl -- get pods -A

5. 네임스페이스

Namespace란?

  • 하나의 물리적 클러스터를 여러 개의 논리적 가상 클러스터로 분할하는 Kubernetes API 리소스입니다.
  • 같은 클러스터 안에서도 dev, staging 같은 Namespace가 각각 독립적인 Service, Pod, ConfigMap, Secret을 가지며, Node·PersistentVolume·ClusterRole 등은 Namespace에 속하지 않고 클러스터 전체에서 공유됩니다.
  • 같은 이름의 리소스도 서로 다른 Namespace에서는 동시에 존재할 수 있습니다(이름은 Namespace 내에서만 고유).

왜 사용하는가?

멀티 테넌시(여러 팀이 클러스터 공유), 환경 분리(dev/staging/production), 리소스 관리(ResourceQuota로 CPU·메모리 제한), 접근 제어(Namespace별 RBAC 정책 적용)에 유용합니다.

클러스터 기본 Namespace

Namespace 설명
default Namespace를 지정하지 않은 경우에 기본적으로 할당되는 Namespace
kube-system 쿠버네티스 시스템에 의해 생성되는 API 오브젝트들을 관리하기 위한 Namespace. 클러스터 레벨의 관리자 영역입니다.
kube-public 모든 사용자로부터 접근 가능하고 읽을 수 있는 오브젝트들을 관리합니다. 누구든 접근 가능하므로 주의가 필요합니다.
kube-node-lease 노드의 연결 정보를 관리합니다. 컨트롤플레인과 노드 간의 연결을 위한 lease 오브젝트를 관리합니다.

API 리소스와 Namespace 범위

모든 API 리소스는 Namespaced(true) 또는 Cluster-scoped(false)로 구분됩니다. kubectl api-resources로 확인하며, --namespaced=true/false 옵션으로 필터링할 수 있습니다.

  • Namespaced: Pod, Service, Deployment, ReplicaSet, ConfigMap, Secret, Role/RoleBinding 등
  • Cluster-scoped: Node, Namespace, PersistentVolume, ClusterRole/ClusterRoleBinding, StorageClass, CRD 등

Namespace 사용하기

  • 조회: kubectl get pods -n <ns>(특정 Namespace) / kubectl get pods --all-namespaces(-A, 전체 조회 시 NAMESPACE 열 추가)
  • 생성: CLI로 kubectl create namespace <name> 또는 YAML(kind: Namespace)을 apply. --dry-run=client -o yaml로 템플릿만 출력할 수 있습니다.
  • Pod 배포: YAML의 metadata.namespace 또는 -n 옵션으로 지정합니다. 둘 다 있으면 YAML 값이 우선합니다.
  • 관리/삭제: kubectl describe namespace, kubectl delete namespace. 삭제 시 내부 모든 리소스가 함께 삭제되며 되돌릴 수 없으므로 사전에 kubectl get all -n <ns>로 확인을 권장합니다.

실무 활용 패턴

환경별(dev/staging/production)로 Namespace를 나누고, 환경마다 다른 ResourceQuota와 RBAC을 적용하는 패턴이 대표적입니다. kubectl config set-context --current --namespace=<ns>로 기본 Namespace를 변경하면 매번 -n을 지정하지 않아도 됩니다.

Namespace 간 통신

Kubernetes 네트워크는 평탄(flat)해서 서로 다른 Namespace의 Pod끼리도 통신 가능합니다. 같은 Namespace 내에서는 Service 이름만으로 접근하지만, 다른 Namespace는 FQDN(<service>.<namespace>.svc.cluster.local)이 필요합니다. Namespace 간 통신을 막으려면 NetworkPolicy를 적용합니다.

ResourceQuota와 LimitRange

  • ResourceQuota: Namespace 전체의 총 리소스 사용량 상한을 설정합니다(예: Pod 최대 10개, CPU 요청 합산 4코어).
  • LimitRange: Namespace 내 개별 Pod/Container 단위로 기본 request/limit 값을 자동 적용합니다.

핵심 명령어 요약

get/create/delete namespace
get pods -n/--all-namespaces
api-resources --namespaced=true/false
config set-context --current --namespace=
create ns --dry-run=client -o yaml

Namespace 실습

Namespace 실습 — Namespace 생성

# CLI로 생성
kubectl create namespace blue

# YAML로 생성 (dry-run으로 YAML 템플릿 추출)
kubectl create namespace green --dry-run -o yaml > green-ns.yaml
kubectl create -f green-ns.yaml

# Namespace 목록 확인
kubectl get namespaces

--dry-run 옵션을 사용하면 실제로 Namespace를 만들지 않고 YAML 파일만 생성해서 코드로 관리할 수 있습니다.

# 01.green-ns.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: green
spec: {}
status: {}

Namespace 실습 — 특정 Namespace에 Pod 배포

# CLI로 Namespace 지정하여 배포
kubectl create -f nginx.yaml -n blue

CLI FIRST — Namespace를 지정한 Pod 생성

$ kubectl run mypod --image=nginx:1.14 --namespace=solcho --dry-run=client -o yaml

--namespace 플래그로 Pod가 생성될 Namespace를 지정합니다. --dry-run=client -o yaml로 실제 적용 전에 YAML 템플릿을 미리 확인할 수 있습니다.

# YAML 파일에 직접 Namespace 지정
apiVersion: v1
kind: Pod
metadata:
  name: mypod
  namespace: orange   # ← Namespace 지정
spec:
  containers:
  - image: nginx:1.14
    name: nginx

Namespace 실습 — Namespace 조회 및 전환

# 특정 Namespace의 Pod 조회
kubectl get pods -n blue

# 모든 Namespace의 Pod 조회
kubectl get pods --all-namespaces

# Namespace 전환 (context 설정)
kubectl config set-context blue@kubernetes \
  --cluster=kubernetes --user=kubernetes-admin --namespace=blue
kubectl config use-context blue@kubernetes

# 현재 context 확인
kubectl config current-context

# 기본 context로 복귀
kubectl config use-context kubernetes-admin@kubernetes
