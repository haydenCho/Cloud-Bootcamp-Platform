AWS 핵심 서비스

AWS(Amazon Web Services)는 서버(EC2), 스토리지, 데이터베이스(RDS), 네트워크(VPC, Route 53), 로드밸런싱과 오토 스케일링, 권한 관리(IAM) 등을 API/콘솔로 즉시 빌려 쓸 수 있게 해주는 퍼블릭 클라우드입니다. 이 단원에서는 EC2 인스턴스를 직접 띄워 웹 서비스를 배포하고, 도메인을 연결하고, 로드밸런서와 오토 스케일링으로 이중화하고, RDS로 데이터베이스를 분리하고, IAM으로 권한을 관리하는 실습 과정에서 얻은 핵심 개념을 정리합니다. 하나의 서버에 모든 걸 몰아넣는 구조(단일 서버) → 로드밸런서 뒤에 여러 대를 두는 구조(수평 확장) → 웹/애플리케이션/데이터베이스를 계층별로 분리하는 구조(N-tier)로 자연스럽게 이어지는 흐름을 따라갑니다.

EC2 (Elastic Compute Cloud)

EC2는 AWS에서 가장 기본이 되는 가상 서버(인스턴스) 서비스입니다. EC2 콘솔의 인스턴스 관리 화면에서 인스턴스를 생성/조회하고, 상태(중지·재부팅·종료)를 제어하고, 콘솔 또는 SSH로 접속할 수 있습니다.

인스턴스 생성 흐름

EC2 인스턴스를 새로 만들 때 순서대로 결정해야 하는 항목은 다음과 같습니다.

  1. 인스턴스 이름 — 콘솔에서 구분하기 위한 태그(Name)
  2. AMI(Amazon Machine Image) — 운영체제 + 초기 설정이 담긴 서버 이미지. 기본 목록에 없는 OS는 "Browse more AMIs"에서 검색해 선택할 수 있다(예: Ubuntu Server 24.04)
  3. 인스턴스 유형 — CPU/메모리 사양. 프리티어 대상 유형(보통 t2.micro/t3.micro)이 있지만, 유료 계정으로 전환하면 프리티어 유형이 안내에서 빠질 수 있다. 이 경우에도 t3 계열이 이전 세대보다 성능 대비 가격이 낫다는 점을 기준으로 선택하면 된다
  4. 키 페어(로그인 키) — 비밀번호 대신 사용할 공개키/개인키 쌍. 새로 생성할 때 형식을 선택하는데, PuTTY로 접속할 경우 .ppk, OpenSSH 계열 클라이언트는 .pem을 사용한다. 개인키 파일은 유출되면 서버가 그대로 뚫리므로 절대 커밋하거나 공유하지 않는다
  5. 네트워크 설정 — 어떤 VPC/서브넷에 배치할지, 퍼블릭 IP 자동 할당 여부, 보안 그룹 등. 기본값으로 생성해도 되지만 각 항목이 무엇을 의미하는지는 알아둘 필요가 있다
  6. 스토리지 구성 — 루트 볼륨(EBS) 크기. 기본값은 8GiB이며, 프리티어 한도(30GiB)까지는 무료이므로 여유 있게 잡아두는 편이 좋다
  7. 고급 설정 — 사용자 데이터(부팅 시 실행 스크립트), 종료 방식 등 다양한 옵션이 있으며, 처음에는 기본값으로 생성해도 무방하다

키 페어와 콘솔 접속

인스턴스가 생성되면 인스턴스 정보에서 퍼블릭 IPv4 주소를 확인할 수 있다. 이 주소로 SSH 클라이언트(PuTTY 등)에서 접속하면 되는데, PuTTY를 쓸 경우 발급받은 .ppk 키를 세션 설정의 인증(Auth) 항목에 등록해야 한다. 접속 계정은 AMI마다 다르며(Ubuntu 계열은 보통 ubuntu), EC2 콘솔의 "인스턴스 연결" 탭에서 어떤 사용자 이름을 써야 하는지 확인할 수 있다.

SSH 클라이언트를 설치하지 않고도 EC2 콘솔의 "EC2 인스턴스 연결" 기능으로 브라우저에서 바로 터미널을 열 수 있다. 원격 접속 프로그램을 준비하기 전에 빠르게 상태를 확인할 때 유용하다.

초기 서버 설정 — 작업 계정과 SSH 보안

인스턴스에 처음 접속하면 루트 계정으로 바로 작업하지 않고, 다음 순서로 별도 작업 계정을 만드는 것이 보안상 권장된다.

# 1) 관리자 권한 획득
sudo su

# 2) 작업용 계정 생성 (루트 계정을 직접 쓰지 않기 위함)
adduser myuser

# 3) sudo 권한 부여: /etc/sudoers
# User privilege specification
root    ALL=(ALL:ALL) ALL
myuser  ALL=(ALL:ALL) ALL

루트 계정으로 그대로 서비스를 운영하면 실수 한 번, 계정 하나가 뚫리는 것만으로 시스템 전체 권한이 넘어간다. 별도 계정을 만들고 필요할 때만 sudo로 권한을 상승시키는 방식이 표준적인 운영 관례다.

SSH 접속 정책은 /etc/ssh/sshd_config(또는 /etc/ssh/sshd_config.d/ 하위의 include 파일)에서 관리한다. 핵심 옵션은 PasswordAuthentication으로, SSH 접속 시 비밀번호 로그인을 허용할지 여부를 결정한다.

# /etc/ssh/sshd_config
# To disable tunneled clear text passwords, change to no here!
PasswordAuthentication yes
#PermitEmptyPasswords no
  • 보안을 강화하려면 no로 설정해 비밀번호 접속을 차단하고 공개키 인증만 허용한다
  • 급하게 비밀번호 접속이 필요한 임시 상황에서는 yes로 활성화한다
  • 클라우드 이미지(예: Ubuntu Cloud Image)는 /etc/ssh/sshd_config.d/ 아래에 별도 설정 파일을 두고 이를 include하는 구조가 많으므로, 메인 설정 파일만 고치고 재기동해도 반영되지 않을 수 있다. 이 경우 include된 하위 설정 파일도 함께 수정해야 한다
# 설정 반영
systemctl restart ssh

보안 그룹(Security Group)

보안 그룹은 인스턴스 단위로 적용되는 가상 방화벽이다. 새로 생성한 인스턴스는 기본적으로 SSH(22번 포트)만 0.0.0.0/0(모든 IP)에 대해 열려 있고, 그 외 포트는 막혀 있다. 웹 서버를 올렸는데 브라우저로 접속이 안 된다면 가장 먼저 의심해야 할 곳이 보안 그룹의 인바운드 규칙이다.

  • 인바운드(Inbound) — 바깥에서 인스턴스로 들어오는 트래픽. 서비스를 열려는 포트(예: HTTP 80, HTTPS 443)마다 규칙을 추가해야 한다
  • 아웃바운드(Outbound) — 인스턴스에서 바깥으로 나가는 트래픽. 기본적으로 전체 허용 상태이며, 특별히 나가면 안 되는 트래픽을 제한할 때만 별도로 설정한다

HTTP 규칙을 추가할 때 프로토콜로 "HTTP"를 선택하면 TCP 80번 포트가 자동으로 채워진다. 모든 클라이언트의 접근을 허용하려면 소스를 "Anywhere-IPv4"로 선택하면 0.0.0.0/0이 자동 입력된다. 반대로 RDS처럼 외부에 노출할 필요가 없는 리소스는 인바운드 소스를 특정 보안 그룹(예: 웹 서버가 속한 보안 그룹)으로 좁혀서, 그 서버를 거치지 않고는 아예 접근이 불가능하게 만드는 것이 좋은 패턴이다.

탄력적 IP(Elastic IP)

EC2 인스턴스는 재부팅할 때마다 퍼블릭 IP가 바뀔 수 있다. 도메인 연결이나 외부 연동 때문에 고정된 IP가 필요하다면 탄력적 IP를 할당해서 인스턴스에 연결한다.

  1. EC2 콘솔의 "탄력적 IP 주소"에서 새 주소를 할당(리전 선택 필요)
  2. 할당된 주소를 선택 → "작업" → "탄력적 IP 주소 연결"
  3. 연결할 인스턴스를 지정하면 해당 인스턴스의 퍼블릭 IP가 이 고정 IP로 유지된다

종료 방지 설정

운영 중인 인스턴스를 실수로 삭제하는 사고를 막기 위해 "인스턴스 설정 → 종료 방지 기능 변경"에서 종료 방지를 활성화할 수 있다. 활성화되어 있으면 콘솔/CLI에서 종료(Terminate)를 시도해도 별도 해제 없이는 삭제되지 않는다.

AMI(이미지)와 시작 템플릿

운영 중인 인스턴스를 표준화된 구성으로 복제하고 싶을 때는 이미지를 생성한다.

  1. 가급적 인스턴스를 중지한 뒤 이미지를 생성한다(스냅샷과 마찬가지로 쓰기 작업이 없는 상태에서 뜨는 것이 안전하다)
  2. "작업 → 이미지 및 템플릿 → 이미지 생성"에서 이름을 지정하면 새로운 AMI가 만들어진다

이렇게 만든 AMI는 시작 템플릿(Launch Template)의 기반이 된다. 시작 템플릿은 AMI, 인스턴스 유형, 보안 그룹 등 인스턴스 생성에 필요한 설정을 미리 묶어둔 것으로, 오토 스케일링 그룹이 새 인스턴스를 만들 때 이 템플릿을 참조한다. 템플릿에는 보통 키 페어를 지정하지 않는다(자동으로 생성되는 인스턴스에 개별 로그인 키를 배정하는 것이 의미가 없기 때문).

웹 서비스 배포와 Nginx 리버스 프록시

EC2 인스턴스 하나에 웹 애플리케이션을 올리는 전형적인 흐름은 (1) 소스코드/실행 환경 준비 → (2) 애플리케이션을 특정 포트에서 실행 → (3) Nginx로 80/443 포트를 받아 내부 애플리케이션 포트로 프록시하는 구조다.

애플리케이션 실행 환경 구성

Python 기반 웹 애플리케이션을 배포한다면 다음과 같은 순서를 거친다.

# 필요 패키지
apt-get install python3-pip
apt install python3.12-venv

# 가상환경 구성
python3 -m venv venv
source ./venv/bin/activate
pip install -r requirements.txt

# DB 서버 설치
apt-get install mariadb-server

DB 접속 정보 같은 민감한 설정은 .env 파일로 분리해 코드와 분리 관리한다.

DB_HOST=localhost
DB_PORT=3306
DB_USER=app_user
DB_PASSWORD=********
DB_NAME=app_db

서비스 실행 스크립트를 작성할 때는 절대경로를 명확히 지정해야 한다. 상대경로나 현재 작업 디렉토리에 의존하면, cron이나 systemd처럼 다른 위치에서 스크립트가 호출될 때 실패한다.

#!/usr/bin/bash

cd /home/app/myservice
source venv/bin/activate
python3 main.py
deactivate

웹 기반 터미널(ttyd)과 옵션 표기 규칙

ttyd는 터미널 프로그램을 웹소켓 기반으로 브라우저에 노출해주는 도구로, 실습/게임/관리 콘솔처럼 브라우저에서 셸 입출력을 주고받아야 하는 서비스에 사용할 수 있다.

apt-get install ttyd -y
nohup ttyd -W bash -c /home/app/run.sh &

-W(--writable)는 클라이언트가 터미널에 입력할 수 있도록 허용하는 옵션이며, 기본값은 읽기 전용이다. 이 옵션을 빼먹으면 페이지에서 키보드 입력이 전혀 먹히지 않는다. 여기서 실무적으로 기억할 규칙 하나는, 한 글자짜리 옵션은 대소문자를 구분하므로(-w와 -W는 다른 옵션) 문서화된 대소문자를 정확히 지켜야 한다는 점이다.

Nginx 리버스 프록시 + WebSocket 설정

Nginx는 외부에서 들어오는 HTTP 요청을 받아 정적 파일은 직접 서빙하고, 동적 처리가 필요한 경로는 내부 애플리케이션(포트)으로 넘겨주는 리버스 프록시 역할을 한다. ttyd처럼 WebSocket을 쓰는 서비스는 업그레이드 헤더를 프록시해줘야 한다.

server {
    listen 80;

    # 정적 랜딩페이지
    location / {
        root /home/app/web;
        index index.html;
    }

    # WebSocket 프록시: /play/ → 내부 포트로 전달 (trailing slash로 경로 prefix 제거)
    location /play/ {
        proxy_pass http://127.0.0.1:7681/;

        # WebSocket 업그레이드
        proxy_http_version 1.1;
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host       $host;

        # 장시간 세션 유지 (예: 12시간)
        proxy_read_timeout 43200s;
        proxy_send_timeout 43200s;
    }
}
# 설정 반영 (문법 오류가 없다면 무중단 재적용)
systemctl reload nginx

Nginx는 /etc/nginx/nginx.conf 외에도 /etc/nginx/sites-available/·/etc/nginx/sites-enabled/ 아래의 사이트별 설정을 함께 참조한다. 두 곳의 설정이 서로 다른 값(예: 다른 IP나 포트)을 가리키고 있으면 어느 한쪽만 고쳐서는 재시작이 실패하거나 원하는 대로 동작하지 않는다. "어느 설정 파일이 실제로 적용되는가"를 먼저 확인하는 습관이 중요하다.

서비스 장애 진단 순서 — 포트 충돌 사례

배포 후 502 Bad Gateway처럼 "일부만 동작하는" 장애가 발생하면 다음 순서로 원인을 좁혀나간다.

  1. 대상 프로세스가 실제로 떠 있는지 확인 
    ps aux | grep ttyd
ss -tlnp | grep 7681
  2. 포트를 두 개의 프로세스가 동시에 쓰려는 경우가 흔한 원인이다. 예를 들어 systemd가 자동으로 띄운 서비스와, 운영자가 nohup으로 수동 실행한 프로세스가 같은 포트를 두고 충돌할 수 있다
  3. 중복 서비스를 정리한다. 
    systemctl stop ttyd
systemctl disable ttyd
  4. 포트가 비었는지 재확인 후 원하는 프로세스만 다시 실행 
    ss -tlnp | grep 7681
nohup ttyd -W bash -c /home/app/run.sh &
  5. 바인딩 주소까지 확인한다. localhost(127.0.0.1)에만 바인딩되어 있으면 같은 서버 안의 다른 프로세스(Nginx 등)에서는 접근할 수 있어도, VPC 내부 IP나 0.0.0.0으로의 접근이 필요한 구조라면 실패한다. 
    curl -I http://<내부IP>:7681

Route 53과 도메인

Route 53은 AWS의 DNS(도메인 이름 시스템) 서비스로, 도메인을 등록하거나 이미 보유한 도메인의 레코드를 관리할 수 있다. 국내 서비스(가비아 등)에서 구매한 도메인도 DNS 설정(네임서버/레코드)만 맞춰주면 동일하게 AWS 리소스와 연결할 수 있다.

DNS 레코드 타입

레코드역할
A도메인 주소를 특정 IPv4 주소와 직접 매핑
CNAME도메인에 다른 도메인 이름(별명)을 부여해 연결(예: 로드밸런서의 DNS 이름을 커스텀 도메인에 연결)
MX해당 도메인으로 들어오는 이메일을 처리할 메일 서버 지정
TXT임의의 텍스트 저장. 스팸 방지(SPF), 이메일 서명 검증(DKIM), 도메인 소유권 인증 등에 사용

가상 호스팅(Virtual Hosting)

가상 호스팅은 서버 한 대(하나의 IP)로 여러 개의 도메인/서비스를 구분해서 서비스하는 방식이다. 클라이언트가 보낸 HTTP 요청의 Host 헤더(어떤 도메인으로 요청했는지)를 기준으로, Nginx가 서로 다른 설정 블록을 선택해 처리해 준다.

  1. 테스트 단계에서 도메인 매핑을 흉내내기 — 실제 도메인을 사기 전에는 로컬 PC의 hosts 파일(C:\Windows\System32\drivers\etc\hosts)에 "IP 도메인" 한 줄을 추가해서, 해당 PC에서만 그 도메인이 특정 서버 IP로 연결되게 할 수 있다
  2. Nginx에 사이트별 설정 파일 작성 — /etc/nginx/sites-available/에 도메인마다 별도 설정 파일을 만든다 
    server {
    listen 80;
    server_name service-a.example.com;

    location / {
        root /usr/share/nginx/html/service-a.example.com;
        index index.html;
    }
}
    • server_name — 이 블록이 응답할 도메인 이름
    • root — 해당 도메인의 정적 파일이 위치한 홈 디렉토리
  3. 사이트 활성화 — sites-available의 설정 파일을 sites-enabled에 심볼릭 링크로 걸어야 실제로 적용된다 
    ln -s /etc/nginx/sites-available/service-a.example.com \
      /etc/nginx/sites-enabled/service-a.example.com
systemctl restart nginx
  4. 도메인별 홈 디렉토리에 콘텐츠 배치 — root로 지정한 경로에 각 사이트의 index.html(및 정적 자원)을 두면, 같은 서버·같은 IP인데도 도메인에 따라 다른 화면이 보이게 된다

ELB(Elastic Load Balancer)

인스턴스를 여러 대로 늘리기 전에 먼저 "여러 대에 트래픽을 어떻게 나눠줄 것인가"를 해결해야 한다. ELB는 하나의 진입점(DNS 이름) 뒤에 여러 인스턴스를 연결하고, 그중 정상적으로 응답하는 인스턴스에만 트래픽을 전달한다.

대상 그룹(Target Group)과 헬스체크

ELB를 만들기 전에 먼저 대상 그룹을 만들어 어떤 인스턴스들을 로드밸런싱 대상으로 묶을지 정의한다. 대상 그룹에는 "상태 검사(Health Check)" 경로와 "성공으로 간주할 상태 코드"(기본값 200)를 지정하는데, 이 상태 검사에서 연속으로 실패하는 인스턴스는 자동으로 트래픽 분배 대상에서 제외된다.

로드밸런서 생성과 확인

대상 그룹을 만든 뒤 ALB(Application Load Balancer)를 생성하면서 방금 만든 대상 그룹을 리스너에 연결한다. 로드밸런서가 프로비저닝되면 자체 DNS 이름이 발급되고, 이 DNS로 접속했을 때 뒤에 연결된 인스턴스 중 하나가 응답하게 된다. 보통 헬스체크용 엔드포인트를 별도로 두는데, 단순히 200 응답만 반환하면 되므로 Nginx에서 최소한의 설정만으로 처리할 수 있다.

server {
    listen 80;

    location /health/ {
        root /usr/share/nginx/html/;
        index index.html;
    }
}

트러블슈팅 — 대상 그룹 Unhealthy

브라우저로 직접 접속하면 정상인데 대상 그룹에서는 "비정상(Unhealthy)"으로 표시되는 경우, 가장 흔한 원인은 대상 그룹이 검사하는 경로와 서버가 실제로 그 경로에 응답하도록 설정된 경로가 서로 다른 것이다.

# 잘못된 예: 실제 URL 경로는 "/" 인데, 파일 시스템 경로에만 /health/가 들어 있음
server {
    listen 80;
    location / {
        root /usr/share/nginx/html/health/;   # URL에는 /health가 드러나지 않는다
        index index.html;
    }
}
# 올바른 예: URL 경로 자체를 /health/ 로 맞춘다
server {
    listen 80;
    location /health/ {
        root /usr/share/nginx/html/;
        index index.html;
    }
}

수정 후 systemctl restart nginx로 반영하면 대상 그룹 상태가 정상으로 바뀐다. 다만 대상 그룹의 상태 갱신에는 검사 주기만큼 시간차가 있으므로, 바로 반영되지 않아도 여유를 두고 확인해야 한다.

트러블슈팅 — 캐시로 인한 302 응답

정적 파일이 브라우저/프록시 어딘가에 캐시되어 있으면 실제 요청이 리다이렉트(302)로 처리되어 대상 그룹이 이를 실패로 판단할 수 있다. Nginx는 이런 상황에서도 헬스체크가 항상 200을 반환하도록 강제하는 설정을 제공한다.

location /health/ {
    access_log off;
    return 200 "ok";
    add_header Content-Type text/plain;
}

헬스체크 엔드포인트는 애플리케이션 로직과 분리해서, 캐싱·리다이렉트·인증 등의 영향을 받지 않는 단순한 응답으로 만들어두는 것이 안전하다.

오토 스케일링(Auto Scaling)

오토 스케일링 그룹(ASG)은 지정한 조건(CPU 사용률 등)에 따라 인스턴스 개수를 자동으로 늘리고 줄여준다. 트래픽이 몰릴 때는 인스턴스를 추가로 띄워 부하를 분산하고, 트래픽이 줄면 다시 인스턴스를 줄여 비용을 절감하는 것이 목적이다.

구성 요소

  1. AMI — 미리 설정을 마친 인스턴스를 이미지로 저장
  2. 시작 템플릿(Launch Template) — 위 AMI, 인스턴스 유형, 보안 그룹 등을 묶어 "이 설정 그대로 인스턴스를 만들어라"는 틀을 정의(키 페어는 보통 지정하지 않는다)
  3. 오토 스케일링 그룹 — 시작 템플릿을 참조하며, 네트워크(가용 영역), 연결할 로드밸런서/대상 그룹, 그룹 크기(최소/원하는/최대 용량)를 지정한다. 로드밸런서를 새로 만들면서 "Internal(내부용)" 여부도 이때 선택할 수 있다

구성이 끝나면 오토 스케일링 그룹, 로드밸런서(프로비저닝에 수 분 소요), 인스턴스가 각각 콘솔에 나타난다. 로드밸런서의 DNS 이름을 Route 53에서 CNAME으로 원하는 도메인에 연결하면, 도메인으로 접속했을 때 오토 스케일링 그룹이 관리하는 인스턴스 중 하나가 응답하게 된다.

부하를 걸어 동작 확인하기

오토 스케일링이 실제로 동작하는지 확인하려면 인위적으로 CPU 부하를 걸어본다.

apt install stress-ng -y

# CPU 코어 2개에 80% 부하를 지속적으로 발생
stress-ng --cpu 2 --cpu-load 80 &

# 지속 시간을 제한하고 싶다면 --timeout 옵션 사용
stress-ng --cpu 2 --cpu-load 80 --timeout 60 &

# 실시간 사용률 확인
htop

CPU 사용률이 스케일링 정책의 임계값을 넘으면 새로운 인스턴스가 자동으로 생성되어 대상 그룹에 등록되는 것을 확인할 수 있다. 반대로 스케일 인(축소)으로 인스턴스가 종료·재생성되는 과정에서는 콘솔에 잠깐 동기화 지연(예: 볼륨 정보 미표시)이 생길 수 있는데, 대부분 새로고침하면 해결된다.

RDS(Relational Database Service)

RDS는 관리형 관계형 데이터베이스 서비스다. 서버에 직접 MySQL/MariaDB/PostgreSQL 등을 설치·운영하는 대신, AWS가 패치·백업·장애 조치 등을 대신 관리해주는 인스턴스를 빌려 쓰는 개념이다. 애플리케이션 서버와 데이터베이스를 분리하는 것은 서버 이중화(오토 스케일링)를 할 때 특히 중요하다 — 각 애플리케이션 서버가 로컬 DB를 따로 가지고 있으면 데이터가 서버마다 달라지므로, 데이터베이스는 반드시 공용 RDS 하나로 모아야 한다.

RDS 생성과 보안 그룹 격리

  1. "데이터베이스 생성 → 표준 생성"에서 엔진(MySQL/MariaDB 등)을 선택한다
  2. 개발/테스트 목적이면 "손쉬운 생성" 템플릿(프리티어 있으면 프리티어)을 사용해 빠르게 만들 수 있다
  3. 마스터 계정 정보를 입력하면 RDS 인스턴스가 생성된다
  4. RDS 전용 보안 그룹을 만들어 인바운드를 애플리케이션 서버가 속한 보안 그룹으로만 제한한다. RDS는 외부에 직접 노출될 이유가 없으므로, "이 애플리케이션 서버들만 접근 가능"하도록 좁혀두는 것이 기본 원칙이다
  5. 운영 중인 RDS의 보안 그룹은 "데이터베이스 수정" 화면에서 나중에 바꿀 수 있으며, 즉시 적용할지 유지보수 예약 시간에 적용할지 선택할 수 있다

온프레미스(로컬) DB → RDS 마이그레이션

기존에 EC2 로컬에서 운영하던 MySQL/MariaDB 데이터를 RDS로 옮길 때는 mysqldump로 백업 파일을 만들고, 그 파일을 RDS 엔드포인트에 그대로 복원하는 방식을 쓴다.

# 전체 백업 (스키마 + 데이터)
mysqldump -u db_user -p app_db > app_db.sql

# 스키마만 백업 (테이블 구조)
mysqldump -u db_user -p app_db --no-data > app_db_schema.sql

# 데이터만 백업
mysqldump -u db_user -p app_db -t > app_db_data.sql

백업 파일에는 대상 데이터베이스가 이미 존재한다고 가정하는 경우가 많으므로, RDS 쪽에는 아직 스키마 자체가 없다면 복원 전에 데이터베이스 생성 구문을 추가해줘야 한다.

CREATE DATABASE IF NOT EXISTS app_db;
USE app_db;
# RDS 엔드포인트로 접속해 백업 파일 복원
mysql -u admin -p -h <RDS_ENDPOINT> < app_db_migration.sql

# 접속 확인
mysql -u admin -p -h <RDS_ENDPOINT>

복원까지 끝나면 애플리케이션의 .env(또는 설정 파일)의 DB 접속 정보를 RDS 엔드포인트로 변경해서, 이후로는 로컬 DB가 아니라 RDS를 바라보도록 전환한다.

IAM(Identity and Access Management)

IAM은 "누가(사용자/역할) 어떤 리소스에 어떤 권한으로 접근할 수 있는가"를 관리하는 서비스다. 사람이 콘솔에 로그인할 때는 IAM 사용자를, EC2 인스턴스 같은 리소스가 다른 AWS 서비스를 호출할 때는 IAM 역할(Role)을 사용한다.

IAM 역할과 EC2 인스턴스 프로파일

EC2에서 실행되는 스크립트나 애플리케이션이 S3, EC2, RDS 같은 다른 AWS 리소스를 호출해야 할 때, Access Key를 코드나 설정 파일에 하드코딩하는 방식은 키가 유출되면 그대로 계정 전체가 위험해지는 안티패턴이다. 대신 다음과 같이 처리한다.

  1. 필요한 권한(정책)을 담은 IAM 역할을 생성한다
  2. 이 역할을 EC2 인스턴스에 연결(인스턴스 프로파일)한다
  3. 인스턴스 안에서 AWS SDK(boto3 등)를 사용하면, 별도의 Access Key 설정 없이도 인스턴스에 연결된 역할의 권한으로 자동 인증된다

AWS SDK/CLI가 자격 증명을 찾는 우선순위는 대략 다음과 같다. ① 코드에서 직접 지정한 값 → ② 환경 변수(AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY) → ③ ~/.aws/credentials 설정 파일(aws configure로 생성) → ④ EC2에 연결된 IAM 역할. 운영 환경에서는 ④(IAM 역할)을 쓰는 것이 키 관리 부담과 유출 위험이 가장 적다.

비용 관리 — 리소스 정리 자동화

실습/테스트가 끝난 뒤 EC2, RDS, 로드밸런서, NAT 게이트웨이, 탄력적 IP처럼 켜져 있는 것만으로 과금되는 리소스를 빠짐없이 정리하지 않으면 예상치 못한 비용이 계속 쌓인다. 리전이 여러 개이고 서비스 종류도 많기 때문에, 콘솔을 리전마다 돌아다니며 눈으로 확인하는 것은 실수가 나기 쉽다. 이런 경우 AWS SDK(boto3)로 "모든 리전을 순회하며 주요 리소스를 찾아 목록화하고, 확인 후 삭제"하는 스크립트를 만들어두면 안전하게 정리할 수 있다.

핵심 아이디어는 다음과 같다.

  • ec2.describe_regions()로 계정에서 활성화된 전체 리전 목록을 가져온다
  • 리전마다 서비스 클라이언트를 새로 만들어(session.client("ec2", region_name=region)) EC2 인스턴스, EBS 볼륨, 탄력적 IP, NAT 게이트웨이, 로드밸런서/대상 그룹, 오토 스케일링 그룹, RDS, Lambda 등을 조회한다
  • S3, IAM, Route 53처럼 리전 개념이 없는(글로벌) 서비스는 리전 순회와 별개로 한 번만 조회한다
  • 각 리소스에 대해 "삭제할까요? [y/n]"으로 확인을 받은 뒤, 동의한 것만 삭제 API를 호출한다 — 삭제는 되돌릴 수 없으므로(특히 RDS·EBS·S3) 자동으로 전부 지우지 않고 반드시 확인 절차를 둔다
import boto3
from botocore.exceptions import ClientError

def get_all_regions():
    ec2 = boto3.client("ec2", region_name="us-east-1")
    resp = ec2.describe_regions(AllRegions=False)
    return sorted(r["RegionName"] for r in resp["Regions"])

def check_ec2_instances(session, region):
    client = session.client("ec2", region_name=region)
    resp = client.describe_instances()
    items = []
    for res in resp.get("Reservations", []):
        for inst in res.get("Instances", []):
            if inst["State"]["Name"] == "terminated":
                continue
            iid = inst["InstanceId"]
            desc = f"[EC2] {iid} - {inst['State']['Name']} - {region}"
            items.append((desc, lambda c=client, i=iid: c.terminate_instances(InstanceIds=[i])))
    return items

def ask_confirm(prompt):
    return input(f"{prompt} [y/n]: ").strip().lower() == "y"

def main():
    session = boto3.Session()
    for region in get_all_regions():
        for desc, delete_fn in check_ec2_instances(session, region):
            if ask_confirm(desc + " -> 삭제할까요?"):
                try:
                    delete_fn()
                    print(f"삭제됨: {desc}")
                except ClientError as e:
                    print(f"삭제 실패: {desc} ({e})")

if __name__ == "__main__":
    main()

범위리소스

미연결(사용하지 않는) 탄력적 IP와 EBS 볼륨은 특히 놓치기 쉬운 비용 항목이다. 인스턴스를 삭제해도 여기에 물려 있던 볼륨/IP는 자동으로 같이 지워지지 않는 경우가 있으므로 별도로 확인해야 한다.

N-tier 아키텍처 구성 — 웹/애플리케이션/DB 분리

서버 한 대에 웹 서버·애플리케이션·데이터베이스를 모두 올리는 구조(1-tier)는 구성은 간단하지만 확장에 한계가 있다. 실습에서는 워드프레스를 예로 웹(WEB)·애플리케이션(WAS)·데이터베이스(RDS)를 계층별로 분리하는 3-tier 구조와, 로드밸런서 뒤에 웹+애플리케이션을 합친 서버를 여러 대 두는 2-tier 구조를 각각 구성해보았다.

3-tier: WEB(Nginx) → WAS(PHP-FPM) → DB(RDS)

WEB 서버는 정적 파일을 직접 서빙하고, PHP로 처리해야 하는 요청만 FastCGI로 WAS 서버에 위임한다.

# WEB 서버(Nginx) 설정
server {
    listen 80;

    root /var/www/html/wordpress;
    index index.php index.html;

    location / {
        try_files $uri $uri/ /index.php?$args;
    }

    # PHP 파일 처리 → WAS 서버로 FastCGI 전달
    location ~ \.php$ {
        fastcgi_pass   <WAS_PRIVATE_IP>:9000;
        fastcgi_index  index.php;

        include        fastcgi_params;
        fastcgi_param  SCRIPT_FILENAME  /var/www/html/wordpress$fastcgi_script_name;
        fastcgi_param  DOCUMENT_ROOT    /var/www/html/wordpress;

        fastcgi_connect_timeout  60s;
        fastcgi_send_timeout     60s;
        fastcgi_read_timeout     60s;
    }
}

WAS 서버에는 PHP-FPM과 워드프레스 실행에 필요한 확장 모듈을 설치하고, PHP-FPM이 네트워크 소켓(TCP)으로 요청을 받도록 설정해서 다른 서버(WEB)에서도 접근할 수 있게 한다.

# 의존 패키지 설치 (WAS)
apt install -y php8.3-fpm php8.3-mysql php8.3-xml \
    php8.3-curl php8.3-gd php8.3-mbstring \
    php8.3-zip php8.3-intl php8.3-soap

# /etc/php/8.3/fpm/pool.d/www.conf
listen = 0.0.0.0:9000

워드프레스 소스는 공식 배포본을 받아 웹 루트에 배치하고, 웹 서버 프로세스(www-data) 소유로 권한을 정리한다.

wget https://ko.wordpress.org/latest-ko_KR.zip
unzip latest-ko_KR.zip
mkdir -p /var/www/html
mv ./wordpress/ /var/www/html/wordpress

chown -R www-data:www-data /var/www
chmod 755 /var/www /var/www/html /var/www/html/wordpress /var/www/html/wordpress/wp-content

systemctl restart php8.3-fpm

WEB과 WAS는 서로 다른 EC2 인스턴스이므로 보안 그룹에서 (1) WEB → 인터넷: HTTP/HTTPS, (2) WAS → WEB: PHP-FPM 포트(9000)만 허용, (3) DB(RDS) → WAS: DB 포트만 허용하는 식으로 계층 간 접근을 최소한으로 열어주는 것이 원칙이다. RDS는 앞서와 마찬가지로 애플리케이션(WAS) 서버의 보안 그룹에서만 접근을 허용하도록 격리한다.

2-tier: ALB → EC2(Nginx + PHP-FPM) → RDS

WEB과 WAS 역할을 한 인스턴스에 합치고, 그 인스턴스를 여러 대 두어 ALB로 분산하는 구조도 가능하다. 이 경우 PHP-FPM은 같은 서버 안에서만 통신하면 되므로 TCP 소켓 대신 유닉스 소켓을 쓰는 것이 조금 더 효율적이다.

# =============================================================
# Nginx 설정 - 2-tier WordPress
# 구성: ALB(HTTPS) → EC2 Nginx(HTTP) → PHP-FPM(유닉스 소켓) → RDS
# =============================================================

server {
    listen 80;
    server_name _;

    root /var/www/html/wordpress;
    index index.php;

    # ALB 헬스체크
    location /health {
        access_log off;
        return 200 "healthy\n";
        add_header Content-Type text/plain;
    }

    # 워드프레스 퍼머링크
    location / {
        try_files $uri $uri/ /index.php?$args;
    }

    # PHP → PHP-FPM(유닉스 소켓) 전달
    location ~ \.php$ {
        try_files $uri =404;
        fastcgi_pass unix:/run/php/php8.3-fpm.sock;
        fastcgi_index index.php;
        include fastcgi_params;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        fastcgi_param HTTP_X_FORWARDED_FOR   $http_x_forwarded_for;
        fastcgi_param HTTP_X_FORWARDED_PROTO $http_x_forwarded_proto;
        fastcgi_read_timeout 300s;
    }

    # 정적 파일은 캐시를 걸어 직접 서빙
    location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff|woff2)$ {
        expires 30d;
        access_log off;
    }

    # 민감 파일 접근 차단
    location ~ /\.(ht|env|git) { deny all; }
    location ~* /wp-config\.php  { deny all; }
    location = /xmlrpc.php       { deny all; }
}

ALB 뒤에서는 X-Forwarded-For / X-Forwarded-Proto 헤더를 통해 원래 클라이언트 IP와 HTTPS 여부를 애플리케이션에 전달해줘야, 애플리케이션이 "실제로는 HTTPS로 들어왔는데 내부적으로는 HTTP로만 보여서" 리다이렉트 루프 같은 문제를 겪지 않는다. wp-config.php, .env, .git처럼 소스/설정 정보가 그대로 노출될 수 있는 경로는 별도로 차단 규칙을 둔다.

배포·마이그레이션 후 흔한 이슈 — DB에 저장된 사이트 URL

워드프레스처럼 애플리케이션이 자신의 접속 주소(도메인/IP)를 데이터베이스에 저장해두는 경우, 서버를 옮기거나(WEB → WAS로 프론트 주소가 바뀌는 등) 로드밸런서/도메인을 새로 붙이면 DB에 남아있는 옛 주소 때문에 리다이렉트가 엉키거나 리소스(CSS/JS/이미지) 경로가 깨질 수 있다. 이럴 때는 RDS에 직접 접속해 저장된 URL 값을 새 주소로 갱신해준다.

# 현재 저장된 사이트 URL 확인
mysql -h <RDS_ENDPOINT> -u admin -p wordpress \
  -e "SELECT option_name, option_value FROM wp_options WHERE option_name IN ('siteurl','home');"

# 새 주소로 갱신
mysql -h <RDS_ENDPOINT> -u admin -p wordpress \
  -e "UPDATE wp_options SET option_value='http://<NEW_ADDRESS>' WHERE option_name IN ('siteurl','home');"

서버 구성을 바꾸는 작업(마이그레이션, 로드밸런서 추가, 도메인 교체 등)을 할 때는 애플리케이션 코드/설정뿐 아니라 데이터베이스에 저장된 자기 참조 정보도 함께 점검해야 한다는 것이 이 사례의 핵심 교훈이다.
