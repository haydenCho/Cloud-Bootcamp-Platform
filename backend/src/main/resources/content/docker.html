종류: 이론 · 날짜: 7월 21일 ~ 7월 24일

VM vs Docker

  • VM
    • 하이퍼바이저 + 게스트 운영체제
    • 하이퍼바이저가 생기면서 하나의 컴퓨터에서 여러 운영체제를 사용할 수 있게 됨
    • 그런데 실제 사용 여부와 별개로 OS를 설치할 때마다 일정 용량을 차지함 → 메모리 차지 多
  • Docker
    • 호스트 운영체제가 반드시 리눅스여야 한다 (리눅스의 특수성 때문!)
    • 도커 엔진 위에 독립적인 컨테이너들을 띄워서 사용
      • 호스트 OS의 리소스를 논리적으로 분리하여 공유
      • 각각의 컨테이너들은 독립되어 있기 때문에 서로 영향을 미치지 못한다
      → 각각의 컨테이너에 OS가 포함되지 않기 때문에 가볍고 빠르다

윈도우에서 도커를 사용할 수 있나?

이전의 수업들에서 WSL을 사용하여 윈도우에서 도커 실습을 간단하게 했다. 도커는 리눅스에서만 사용할 수 있다고 했는데 어떻게 그게 가능했을까?

윈도우 WSL-Docker 구성

  1. 윈도우에는 자체 하이퍼바이저가 있다
  2. 이 하이퍼바이저 위에 WSL로 리눅스 환경을 구축
  3. WSL로 구축한 리눅스 환경에 Docker Engine을 구축
  4. 엔진 위에 여러개의 컨테이너들을 띄워서 사용

도커의 세 가지 특징

  1. chroot: 독립된 공간 형성
    • chroot(Change Root)는 특정 프로세스가 바라보는 루트 디렉토리(/)를 변경하는 기술
    • 만약 이 기능이 제공되지 않는다면 컨테이너가 호스트 파일 전체에 접근이 가능하다
  2. Namespace: 6가지 isolate 공간 제공
    • 한 덩어리의 데이터에 이름을 붙여 충돌 가능성을 줄이고, 프로세스가 시스템 자원을 독립적으로 사용하게 하는 개념
    • 포트 충돌, PID 충돌, 타 컨테이너 프로세스 열람을 방지한다
    • Linux Namespace의 종류
      • PID namespace: 프로세스 ID 격리 / namespace가 다른 프로세스끼리는 서로 액세스할 수 없음
      • Network namespace: IP, Port, 라우팅 테이블 등 네트워크 리소스 격리 / 호스트에서 사용 중인 포트도 컨테이너 안에서 동일하게 사용 가능
      • UID namespace: 사용자(UID)와 그룹(GID) ID 격리 / 호스트와 컨테이너가 서로 다른 권한 체계를 가질 수 있음
      • Mount namespace: 격리된 파일 시스템 트리를 제공하여 호스트와 독립된 마운트 지점을 가짐
      • UTS namespace: namespace별로 호스트명이나 도메인명을 독자적으로 가질 수 있음
      • IPC namespace: 프로세스 간 통신(IPC) 오브젝트를 독립적으로 관리

격리의 핵심 원리

컨테이너는 하나의 리눅스 프로세스다. 다만 위 6가지 Namespace가 씌워져 마치 별개의 서버처럼 느껴질 뿐이다.

격리된 프로세스 환경에 접속하는 명령어:

docker exec -it [컨테이너명] /bin/bash
  1. cgroup: 필요한 만큼의 HW 지원
    • cgroup(Control Groups)은 컨테이너가 호스트의 자원을 효율적으로 공유하면서도, 특정 프로세스가 자원을 독점하지 못하도록 제어
      • 자원 제한: CPU 코어, 메모리 사용량, 네트워크 대역폭 등을 그룹별로 제한
      • 우선순위: 특정 그룹에 더 많은 자원을 할당하는 가중치 설정이 가능
      • 모니터링: 그룹별 자원 사용량을 실시간으로 통계 가능
    • 이 기능이 없으면 컨테이너 1개가 CPU 100% 독점 → 서버 다운
cgroup 제어 대상docker run 옵션사용 예시 및 효과
메모리 (RAM)-m 또는 --memory-m 512m → 512MB 초과 시 컨테이너 강제 종료(OOM Kill)
CPU 코어--cpus--cpus="1.5" → 최대 1.5 코어만 사용 가능
CPU 우선순위--cpu-shares--cpu-shares=512 → 기본값(1024) 대비 절반의 CPU 가중치 부여
메모리 스왑--memory-swap--memory-swap=1g → RAM+SWAP 합산 최대 1GB 제한

도커 네트워크

  • 도커에도 가상머신의 Bridge, NAT, host-only와 비슷한 네트워크 설정들이 있지만 어떤 것을 쓰든 외부와의 통신은 불가능하다.
  • 외부와의 통신을 원한다면 포트포워딩이 필요하다.

도커의 구성요소

도커 이미지(Docker Image) == 클래스

  • 한 번 만들어지면 절대 변하지 않는 읽기 전용(Read-Only) 템플릿
  • 컨테이너를 실행하면 도커는 이 이미지 위에 데이터를 쓰고 지울 수 있는 레이어(Read-Write Layer)를 추가한다
    • 컨테이너 안에서 기존 이미지의 파일을 수정하려고 하면, 도커는 원본 파일을 건드리지 않고 최상단의 R/W 레이어로 원본을 '복사'해 온 뒤 수정한다 → 컨테이너가 삭제되면 이 R/W 레이어만 날아가고, 원본은 안전하게 유지된다

도커 컨테이너(Docker Container) == 인스턴스

  • 호스트 컴퓨터 OS 상에 논리적인 구획을 나누어 분리
  • 애플리케이션 구동을 위한 라이브러리(Bins/Libs)를 모아 별도의 서버처럼 사용
  • 호스트 컴퓨터의 리소스를 논리적으로 분리하여 여러 컨테이너가 공유하여 사용

도커 컨테이너(Docker Container)의 생명주기

명령어설명
docker create이미지로부터 격리된 파일 시스템(R/W 레이어)을 만들지만 실행하지는 않은 대기 상태(Created)를 만든다
docker start중지(Exited)되거나 대기(Created) 중인 컨테이너의 프로세스를 메모리에 올려 실행(Running)시킨다
docker runpull(이미지 다운로드) + create(생성) + start(실행)를 한 번에 수행하는 가장 자주 쓰이는 명령어
docker stop실행 중인 프로세스에 정상 종료 시그널(SIGTERM)을 보내 안전하게 종료(Exited)시킨다. 데이터는 유지됨
docker rm종료된 컨테이너의 R/W 레이어를 디스크에서 완전히 삭제(Deleted)한다

도커 네이밍 규칙

  • docker run hello-world
    • 생략된 주소: docker.io/library (기본적으로 탐색하는 공식 홈페이지)
    • 생략된 버전: latest
    • 전체 커맨드: docker run docker.io/library/hello-world:latest

도커-이미지-컨테이너 요약(예시)

도커(Docker), 이미지, 컨테이너를 요리/식당 비유로 설명한다.

이미지(Image) = 레시피
완성된 요리를 만들기 위한 재료와 조리법이 전부 적힌 설계도다. 예를 들어 "우분투 + Node.js + 내 앱 코드"를 담은 이미지는 한 번 만들어두면 변하지 않는다(불변). 레시피 자체는 먹을 수 없듯, 이미지도 그 자체로는 실행되지 않는다.

컨테이너(Container) = 레시피로 실제 만든 요리
이미지(레시피)를 실행하면 컨테이너(실제 돌아가는 요리)가 된다. 같은 레시피로 요리를 여러 접시 만들 수 있듯, 하나의 이미지로 컨테이너 여러 개를 동시에 띄울 수 있다. 각 컨테이너는 서로 격리돼 있어서 하나가 망가져도 다른 것에 영향을 안 준다.

도커(Docker) = 주방 시스템
레시피(이미지)를 보관·공유하고, 요리(컨테이너)를 만들고 치우는 걸 관리하는 전체 도구다.

명령어로 흐름을 보면:

docker build   → 레시피 작성 (이미지 생성)
docker run     → 요리 시작 (컨테이너 실행)
docker stop/rm → 요리 치우기 (컨테이너 종료/삭제)

핵심 한 줄 정리: 이미지는 "클래스", 컨테이너는 그 클래스로 만든 "인스턴스"라고 보면 개발자에겐 가장 직관적이다.

레이어(Layer) 구조 — 겹겹이 쌓은 투명 필름

이미지는 한 덩어리가 아니라 여러 층이 쌓인 구조다. Dockerfile의 명령어 하나하나가 새 레이어를 만든다.

FROM ubuntu        ← 레이어 1 (베이스 OS)
RUN apt install ~  ← 레이어 2 (패키지 설치)
COPY . /app        ← 레이어 3 (내 코드)

핵심은 두 가지다. 첫째, 캐시. 코드(레이어 3)만 바뀌면 위층만 다시 만들고 아래층(1, 2)은 재사용한다. 그래서 빌드가 빨라진다. 둘째, 공유. 여러 이미지가 같은 베이스 레이어를 쓰면 디스크에 한 번만 저장된다. 레이어는 읽기 전용이고, 컨테이너를 실행하면 맨 위에 쓰기 가능한 층 하나가 얹힌다.

볼륨(Volume) — 외장 하드

컨테이너는 삭제하면 안의 데이터도 같이 사라진다(요리 치우면 접시도 비워짐). DB 데이터처럼 살아남아야 하는 건 컨테이너 밖에 저장해야 하는데, 그게 볼륨이다. 컨테이너에 꽂는 외장 하드라고 보면 된다.

docker run -v mydata:/var/lib/mysql mysql

컨테이너를 지웠다 다시 만들어도 mydata 볼륨은 그대로 남는다. 컨테이너의 수명과 데이터의 수명을 분리하는 게 핵심이다.

네트워크(Network) — 컨테이너들의 전화망

컨테이너는 기본적으로 서로 격리돼 있다. 웹 서버 컨테이너가 DB 컨테이너와 통신하려면 같은 네트워크에 묶어야 한다. 같은 네트워크에 있으면 IP 대신 컨테이너 이름으로 서로를 부를 수 있다.

docker network create mynet
docker run --network mynet --name db postgres
docker run --network mynet --name web myapp
# web 안에서 "db"라는 이름으로 접속 가능

외부(내 브라우저)에서 접속하려면 포트를 열어줘야 한다. -p 8080:80은 "내 컴퓨터 8080 → 컨테이너 80"으로 연결하는 문(door)이다.

세 줄 요약: 레이어는 이미지를 빠르고 가볍게, 볼륨은 데이터를 오래, 네트워크는 컨테이너끼리 대화하게 만드는 장치다.

docker run -d 옵션

  • detach
  • 컨테이너를 백그라운드로 실행하는 옵션
  • 사용하지 않으면 프로세스 과정이 전부 포그라운드로 실행됨

이미지 다운로드 - 레이어로 이해하기

  • 여러개의 id들을 병렬적으로 다운로드
    • 각각의 id들은 이미지를 이루는 레이어들의 id
    • 이미지를 다운받을 때 이미 존재하는 레이어는 중복으로 다운받지 않음

도커의 장점!

이미지와 컨테이너를 레이어로 구성한다
→ 이미지를 다운받을 때 중복된 내용을 다운로드 받지 않고 공유함
→ 컨테이너를 삭제할 때 컨테이너 레이어만을 삭제함

이미지 생성 & Compose

이미 정리한 내용(VM vs Docker, chroot·namespace·cgroup, 컨테이너 생명주기, run/-v/-d, inspect, 컨테이너 IP로 연동한 3-tier 등)은 빼고, 오늘 배운 "이미지 생성"과 "Compose"만 정리했다.

지난 시간까지는 남이 만든 이미지(nginx, mariadb…)를 가져다 쓰기만 했다. -v로 소스를 마운트하고, 컨테이너를 하나씩 띄우고, 컨테이너 IP를 손으로 찾아서 연동했다. 오늘부터는 ① 내 이미지를 직접 만들고(이미지 생성), ② 여러 컨테이너를 한 방에 정의·실행(Compose)한다.

Part 1. 이미지 생성 (Build)

왜 이미지를 만드나?

지난 게임/3-tier 실습을 떠올려 보자.

# 지금까지 방식: nginx 이미지 + 내 소스를 -v로 마운트
docker run -d --name web -p 80:80 -v ./html:/usr/share/nginx/html:ro nginx

이 방식은 소스 파일이 호스트에 있어야만 동작한다. 다른 서버로 옮기면 소스도 같이 복사해서 경로를 맞춰야 하고, 마운트도 다시 걸어야 한다.

핵심 전환
이미지를 만든다 = 애플리케이션 + 실행 환경을 하나의 파일(이미지)로 통째로 굳힌다.
→ 이 이미지 하나만 있으면 어디서든 docker run 한 줄로 똑같이 실행된다.
→ "내 컴퓨터에선 되는데요?" 문제가 사라진다.

이미지를 만드는 방법은 두 가지다.

방법설명실무
docker commit실행 중인 컨테이너를 그대로 스냅샷 떠서 이미지로잘 안 씀 (비추)
docker build + Dockerfile레시피(Dockerfile)를 작성해서 이미지를 빌드표준 방식

방법 A. docker commit (개념만)

# 1. 컨테이너에 들어가 뭔가 설치/수정
docker exec -it mycontainer /bin/bash
# (안에서 apt install ~ 등 작업)

# 2. 그 상태를 이미지로 저장
docker commit mycontainer myimage:1.0
  • 컨테이너의 현재 상태를 그대로 이미지로 박제한다.
  • 문제: 안에서 무슨 짓을 했는지 기록이 안 남는다(재현 불가). 그래서 실무에선 거의 안 쓰고, Dockerfile을 쓴다.

방법 B. Dockerfile + docker build (표준)

Dockerfile = 이미지를 만드는 레시피(설계도)
요리 비유를 이어가면: 지난번엔 완성된 레시피(nginx 이미지)를 사서 썼다면, 이제는 내가 레시피를 직접 쓴다.

Dockerfile 기본 구조

파일 이름은 그냥 Dockerfile (확장자 없음).

# 1. 베이스 이미지 (바닥 레이어) - 어떤 OS/런타임 위에서 시작할지
FROM node:20

# 2. 컨테이너 안 작업 디렉토리 지정 (이후 명령의 기준 경로)
WORKDIR /app

# 3. 호스트 파일을 이미지 안으로 복사
COPY package.json .
RUN npm install          # 4. 빌드 중 실행할 명령 (패키지 설치)
COPY . .

# 5. 이 컨테이너가 쓰는 포트 문서화 (실제 개방은 -p 로)
EXPOSE 3000

# 6. 컨테이너가 시작될 때 실행할 명령
CMD ["node", "server.js"]

주요 명령어(instruction) 정리

명령어역할예시
FROM베이스 이미지 지정 (반드시 첫 줄)FROM ubuntu:22.04
WORKDIR작업 디렉토리 설정·이동 (없으면 생성)WORKDIR /app
COPY호스트 파일/폴더 → 이미지 안으로 복사COPY . /app
ADDCOPY + 압축 자동 해제 + URL 다운로드ADD app.tar.gz /app
RUN빌드 시점에 실행 (패키지 설치 등)RUN apt update && apt install -y curl
CMD실행 시점에 실행할 기본 명령 (덮어쓰기 가능)CMD ["nginx", "-g", "daemon off;"]
ENTRYPOINT실행 시점 고정 명령 (덮어쓰기 어려움)ENTRYPOINT ["python"]
ENV환경변수 설정ENV NODE_ENV=production
ARG빌드 때만 쓰는 변수 (--build-arg)ARG VERSION=1.0
EXPOSE사용하는 포트 문서화 (개방 X)EXPOSE 80
VOLUME볼륨 마운트 지점 지정VOLUME /var/lib/mysql

RUN vs CMD vs ENTRYPOINT — 헷갈리는 3형제

  • RUN: 이미지를 만드는 중에 실행 (예: 패키지 설치). 결과가 레이어로 굳는다.
  • CMD: 컨테이너를 띄울 때 실행되는 기본 명령. docker run 이미지 <명령>으로 덮어쓸 수 있다.
  • ENTRYPOINT: 항상 실행되는 고정 명령. CMD는 그 뒤에 붙는 "기본 인자"처럼 동작.

지난번 inspect에서 본 nginx의 "Cmd": ["nginx","-g","daemon off;"]가 바로 이 CMD다!

EXPOSE ≠ 포트 개방
EXPOSE는 "이 이미지는 80포트를 씁니다"라는 메모(문서)일 뿐, 외부로 열어주지 않는다. 실제 외부 연결은 지난번처럼 docker run -p 80:80으로 해야 한다. (헷갈리기 쉬움!)

레이어 & 빌드 캐시 (★중요)

지난 노트에서 "이미지는 레이어로 쌓인다, 중복 레이어는 재사용한다"까지 정리했다. 빌드에서 이게 속도로 직결된다.

Dockerfile의 명령어 한 줄 = 레이어 하나
빌드할 때 도커는 위에서부터 각 줄을 실행하며 레이어를 쌓는다. 바뀌지 않은 줄은 캐시(이전 레이어)를 재사용하고, 바뀐 줄부터 다시 만든다.

그래서 순서가 성능을 결정한다.

# ❌ 나쁜 순서 - 코드 한 줄만 바꿔도 npm install을 매번 다시 함
COPY . .
RUN npm install

# ✅ 좋은 순서 - 의존성 파일이 그대로면 npm install 캐시 재사용
COPY package.json .
RUN npm install       # package.json 안 바뀌면 이 레이어 캐시됨 (빠름!)
COPY . .              # 소스만 바뀌면 여기부터 다시

원칙: 자주 안 바뀌는 것 → 위, 자주 바뀌는 것(소스 코드) → 아래
이렇게 해야 캐시를 최대한 재사용해서 빌드가 빨라진다.

.dockerignore

.gitignore의 도커 버전. 빌드 시 이미지에 넣지 않을 것들을 지정한다.

node_modules
.git
*.log
.env
  • COPY . . 할 때 불필요한 파일(용량 큰 것, 비밀번호 등)이 이미지에 딸려 들어가는 걸 막는다.
  • 빌드 속도 ↑, 이미지 크기 ↓, 보안 ↑.

docker build 실행

# 문법: docker build -t <이미지이름>:<태그> <Dockerfile 있는 경로>
docker build -t myapp:1.0 .
  • -t: 이미지 이름(tag) 지정. 안 주면 이름 없이 ID만 생김.
  • 맨 끝 .: 빌드 컨텍스트 = Dockerfile과 COPY 대상 파일들이 있는 폴더 (현재 디렉토리).

빌드 후 확인 → 실행:

docker images                       # 만든 이미지 확인
docker run -d -p 8080:3000 myapp:1.0   # 만든 이미지로 컨테이너 실행

build → run 흐름 (요리 비유 완성)
docker build = 레시피(Dockerfile)로 밀키트(이미지) 제작
docker run = 밀키트를 데워서 요리(컨테이너) 완성
지난번엔 남의 밀키트를 샀고, 이제는 내 밀키트를 만든다.

태그(tag)와 레지스트리에 올리기 (push)

지난번에 배운 네이밍 규칙(docker.io/library/nginx:latest)을 그대로 쓴다. 내가 만든 이미지를 Docker Hub 같은 저장소에 올리려면 이름을 규칙에 맞게 붙인다.

# 1. 로그인
docker login

# 2. <계정명>/<이미지명>:<태그> 형식으로 태그 지정
docker tag myapp:1.0 solcho/myapp:1.0

# 3. 올리기
docker push solcho/myapp:1.0

# 다른 곳에서 받기 (지난번 pull과 동일)
docker pull solcho/myapp:1.0

(참고) 멀티스테이지 빌드

빌드에 필요한 도구(컴파일러 등)는 무겁다. 최종 이미지에는 결과물만 남기고 싶을 때 쓴다.

# 1단계: 빌드용 (무거운 환경)
FROM node:20 AS builder
WORKDIR /app
COPY . .
RUN npm install && npm run build

# 2단계: 실행용 (가벼운 환경) - 1단계 결과물만 복사해 옴
FROM nginx:alpine
COPY --from=builder /app/dist /usr/share/nginx/html
  • 최종 이미지에는 node:20(빌드 도구)이 안 들어가고 nginx:alpine만 남는다 → 훨씬 가벼움.
  • 지금 당장 안 써도 되지만 "이미지 경량화" 키워드로 기억해두면 좋다.

Part 2. Docker Compose

왜 Compose를 쓰나?

지난 시간에 한 3-tier(nginx–tomcat–mariadb) 실습을 떠올려 보자. 이런 식이었다.

# 컨테이너 하나하나 손으로 띄우고
docker run -d --name mydb --env MARIADB_... -p 3306:3306 mariadb
docker run -d --name was ...
# nginx 설정에 톰캣 IP(172.17.0.3)를 직접 박아넣고
# proxy_pass http://172.17.0.3:8080;
docker run -d --name web -p 80:80 -v ...:ro nginx

이 방식의 불편함:

  • 컨테이너를 여러 번 나눠서 실행해야 함
  • 컨테이너 IP를 손으로 찾아서 설정에 박아야 함 (172.17.0.3 등) — 재시작하면 IP가 바뀔 수도!
  • 실행 순서(DB 먼저 → WAS → WEB)를 사람이 챙겨야 함
  • 정리(삭제)할 때도 하나하나 rm

Docker Compose = 여러 컨테이너를 YAML 파일 하나로 정의하고, 명령 하나로 전부 실행/정리
지난번의 여러 docker run 명령을 docker-compose.yml 파일 하나로 대체한다. docker compose up 한 줄이면 DB·WAS·WEB이 알아서 순서대로 뜬다.

docker-compose.yml 구조

프로젝트 폴더에 docker-compose.yml 파일을 만든다. (YAML = 들여쓰기가 문법! 탭 금지, 공백 2칸)

services:                    # 띄울 컨테이너들(=서비스) 목록
  web:                       # 서비스 이름 (컨테이너 별명이자 호스트명이 됨!)
    image: nginx:latest      # 사용할 이미지
    ports:
      - "80:80"              # 지난번 -p 80:80 과 동일
    volumes:
      - ./web/conf:/etc/nginx/conf.d:ro   # 지난번 -v 와 동일
    depends_on:
      - was                  # was가 먼저 뜬 뒤 web 실행

  was:
    image: tomcat:9
    # image 대신 내 Dockerfile로 빌드하려면:
    # build: ./was
    expose:
      - "8080"               # 내부 통신용 (외부 개방 X)
    depends_on:
      - db

  db:
    image: mariadb:latest
    environment:             # 지난번 --env 들과 동일
      MARIADB_USER: solcho
      MARIADB_PASSWORD: "1234"
      MARIADB_DATABASE: solchodb
      MARIADB_ROOT_PASSWORD: qwer
    volumes:
      - dbdata:/var/lib/mysql   # 이름 있는 볼륨 (데이터 영속)

volumes:                     # 이름 있는 볼륨 선언
  dbdata:

docker run 옵션 ↔ Compose 대응표

★ 서비스 이름 = 자동 통신 (Compose의 핵심 장점)

지난번 3-tier에서 nginx 설정에 톰캣 IP를 직접 박았던 걸 기억하자.

proxy_pass http://172.17.0.3:8080;   # ← IP를 손으로 찾아 박음 (불편/불안정)

Compose는 같은 파일 안의 서비스끼리 자동으로 같은 네트워크에 묶고, 서비스 이름을 호스트명처럼 쓸 수 있게 해준다 (내부 DNS 제공).

proxy_pass http://was:8080;          # ← IP 대신 서비스 이름 "was"!

지난 노트의 "같은 네트워크에 있으면 IP 대신 컨테이너 이름으로 부를 수 있다"가 Compose에서 자동으로 실현된다. IP를 찾을 필요가 없어진다.

  • DB 접속도 jdbc:mysql://db:3306/solchodb 처럼 서비스 이름 db를 그대로 씀.

Compose 명령어

프로젝트 폴더(docker-compose.yml 있는 곳)에서 실행한다.

명령어역할
docker compose upyml대로 전부 생성·실행 (포그라운드, 로그 보임)
docker compose up -d백그라운드로 전부 실행 (지난번 -d와 동일)
docker compose up -d --build이미지 새로 빌드하고 실행 (build: 쓸 때)
docker compose down컨테이너·네트워크 전부 정지·삭제 (한 방 정리)
docker compose down -v볼륨까지 삭제 (데이터도 날아감, 주의)
docker compose ps실행 중인 서비스 목록
docker compose logs -f전체 로그 실시간 보기 (-f = follow)
docker compose logs -f web특정 서비스(web) 로그만
docker compose stop / start삭제 없이 정지 / 재시작
docker compose exec web bash실행 중 서비스에 접속 (지난번 docker exec와 동일)

명령어가 두 종류로 보일 수 있다.

  • docker compose ... (띄어쓰기): 최신 방식(플러그인). 설치 때 넣은 docker-compose-plugin이 이것.
  • docker-compose ... (하이픈): 구버전. 지금은 docker compose를 쓰면 된다.

depends_on 주의점

depends_on:
  - db
  • depends_on은 실행 순서만 보장한다 (db 컨테이너를 web보다 먼저 "시작").
  • 하지만 db 안의 프로세스(MariaDB)가 접속 받을 준비까지 됐는지는 보장하지 않는다.
  • 지난 노트에서 본 "그냥 start하면 준비 안 돼서 꺼진다"와 비슷한 맥락 → 앱 쪽에서 재시도 로직이나 healthcheck로 보완한다.
db:
  image: mariadb:latest
  healthcheck:
    test: ["CMD", "healthcheck.sh", "--connect"]
    interval: 5s
    retries: 10

한눈 요약

이미지 생성과 Compose 두 가지가 이 단원의 핵심이다.

  1. 이미지 생성 — 남의 이미지에 -v로 소스를 얹던 방식에서 벗어나, Dockerfile(레시피)을 써서 docker build로 내 이미지를 굳힌다. 레이어·캐시 순서(안 바뀌는 것 위로)가 빌드 속도의 핵심이고, .dockerignore로 불필요한 파일을 뺀다. 만든 이미지는 tag → push로 배포한다.
  2. Docker Compose — 지난 3-tier에서 컨테이너를 하나씩 run하고 IP를 손으로 박던 걸, docker-compose.yml 하나로 정의하고 docker compose up -d 한 줄로 전부 띄운다. 서비스 이름이 곧 호스트명이라 IP를 찾을 필요가 없고, down 한 줄로 깔끔하게 정리된다.
Dockerfile  →  docker build  →  내 이미지
                                   │
여러 이미지  →  docker-compose.yml  →  docker compose up -d  →  전체 서비스 기동

이미지 박제 · 압축 전달

  • 네트워크 생성 및 사용
  • 이미지 생성
  • 이미지 업로드
    • 이미지 박제: commit <컨테이너 이름 혹은 id> <이미지 이름>:[태그(버전)]
    • 이미지 추출(압축): save -o <압축 파일 이름(ex. out.tar)> <이미지 이름> (-o: output)
    • 이미지 복원(해제): load -i <압축 파일 이름> (-i: input)

이미지를 생성하고 압축해서 전달하는 방식도 쓴다. 회사에서는 이미지를 도커 허브에 배포(push+pull)해서 쓰기도 함(많이는 안 씀).

이처럼 직접 도커 컨테이너를 생성하고 수정한 다음 이미지 생성을 하면 개발 과정에서 수정할 때마다 이미지를 다시 생성하고 업로드 과정을 해야 함 → 불편하다! 그래서 도커 컴포즈를 사용한다.

도커 컴포즈(Docker Compose) 옵션 정리

최소 옵션 — 실무에서 실제로 자주 쓰는 것만

services:
  서비스이름:
    image: 이미지:태그        # 쓸 이미지. (직접 빌드하면 image 대신 build: .)
    container_name:          # 컨테이너 이름 (고정 이름)
    ports:
      - "호스트:컨테이너"      # 예) "8080:80"  외부 노출이 필요할 때만
    environment:             # 설정값 주입 (또는 env_file: .env 로 파일 분리)
      키: 값
    volumes:
      - 볼륨:/데이터/경로      # DB 등 데이터 유지가 필요할 때
    depends_on:
      - 다른서비스            # 시작 순서 (DB 먼저 등)
    restart: unless-stopped   # 죽으면 자동 재시작

volumes:
  볼륨:                       # 위에서 명명 볼륨 썼으면 여기 선언

옵션 레퍼런스 (전체)

최신 Compose Spec 기준. 상단 version: 키는 더 이상 필요 없다.

services:
  서비스이름:                    # 원하는 이름. 다른 서비스에서 이 이름=호스트명으로 접근
    # ── 이미지 / 빌드 ──────────────────────────────
    image: 이미지:태그            # 사용할 이미지. 예) postgres:16-alpine (latest 지양)
    build:                        # Dockerfile로 직접 빌드할 때
      context: .                  # Dockerfile이 있는 경로
      dockerfile: Dockerfile      # 파일명 (기본값 Dockerfile)
      args:                       # 빌드 시점(ARG)에 넘길 변수
        키: 값
    container_name: 고정이름       # 컨테이너 이름 고정 (보통 생략, 자동 생성 권장)

    # ── 실행 제어 ─────────────────────────────────
    command: 실행명령              # 컨테이너 시작 시 실행할 명령 (Dockerfile CMD 덮어씀)
    entrypoint: 진입점             # ENTRYPOINT 덮어씀
    restart: unless-stopped        # no | always | on-failure | unless-stopped
    working_dir: /app              # 명령 실행 기준 디렉터리
    user: "1000:1000"             # 실행 유저(uid:gid). 보안상 non-root 권장

    # ── 포트 ──────────────────────────────────────
    ports:
      - "호스트:컨테이너"           # 예) "8080:80" → 외부 8080 → 내부 80
      - "127.0.0.1:5432:5432"     # 특정 IP에만 바인딩 (외부 노출 차단)
    expose:
      - "포트"                     # 같은 네트워크 내부에만 열기 (호스트엔 노출 X)

    # ── 환경 변수 ─────────────────────────────────
    environment:                   # 개별 환경변수 지정
      키: 값
      DATABASE_URL: ${DB_URL}     # ${} 로 .env / 셸 변수 주입
    env_file:
      - .env                       # 파일에서 한꺼번에 로드 (민감정보는 여기로)

    # ── 볼륨 (데이터 영속 / 파일 마운트) ──────────────
    volumes:
      - 명명볼륨:/컨테이너/경로      # 예) db-data:/var/lib/postgresql/data (데이터 유지)
      - ./호스트경로:/컨테이너경로   # 바인드 마운트 (호스트 파일 직접 연결)
      - ./설정:/etc/config:ro      # :ro = 읽기 전용

    # ── 의존성 / 시작 순서 ────────────────────────
    depends_on:
      다른서비스:
        condition: service_healthy # service_started | service_healthy | service_completed_successfully

    # ── 헬스체크 ─────────────────────────────────
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost/health"]  # 성공 판단 명령
      interval: 30s                # 검사 주기
      timeout: 5s                  # 응답 대기 한계
      retries: 3                   # 실패 몇 번이면 unhealthy
      start_period: 40s            # 초기 부팅 유예 (이 동안 실패는 무시)

    # ── 네트워크 ─────────────────────────────────
    networks:
      - 네트워크이름                # 이 서비스가 속할 네트워크 (같은 망끼리만 통신)

    # ── 자원 제한 ─────────────────────────────────
    deploy:
      resources:
        limits:                    # 상한
          cpus: "1.0"              # CPU 코어 수
          memory: 512M             # 메모리 상한
        reservations:              # 최소 보장
          memory: 256M
    # (단일 호스트에서 limits만 쓸 땐 mem_limit / cpus 로도 지정 가능)

    # ── 로깅 ─────────────────────────────────────
    logging:
      driver: "json-file"          # 로그 드라이버
      options:
        max-size: "10m"            # 파일당 최대 크기 (로테이션)
        max-file: "3"              # 보관 개수 (디스크 폭주 방지)

# ── 최상위: 명명 볼륨 선언 ─────────────────────────
volumes:
  db-data:                         # services에서 참조한 명명 볼륨은 여기 선언
    driver: local                  # (기본 local, 보통 생략)

# ── 최상위: 네트워크 선언 ──────────────────────────
networks:
  네트워크이름:
    driver: bridge                 # 기본 bridge (보통 생략)
    internal: true                 # true면 외부 인터넷 차단 (내부 전용)
